# 02.2 — 式と優先順位

> **Status:** 実装済み / 仕様策定済み / 計画中 (IMPLEMENTED / SPECIFIED / PLANNED)
> **概要:** パーサーは文法を実装し、型チェッカーは演算子、`if` の分岐、enum の型付き `match` も検査します。インデックスの意味は未決定です。

優先順位は書式の些事ではありません。`a + b * c` は、準拠するどの実装でも
ただ一つの意味を持たなければなりません。そしてパーサーはまさにその形を生成します。
`1 + 2 * 3` の木では、乗算が内側のノードになり、加算がその上に来ます。

これらはもう未解決の問いではありません。文法レベルの連鎖として
[`grammar/nudo.ebnf`](https://github.com/smouj/nudo/blob/main/grammar/nudo.ebnf)
に一度だけ記述され、それを説明する二つの文書に同一の内容で複製され、
[`scripts/check-grammar.py`](https://github.com/smouj/nudo/blob/main/scripts/check-grammar.py)
によって機械的に検査されています。

- 後置演算は単項演算子より強く結合し、連鎖するため、`a.b(c)[d]` は一つの式です。
- 乗算と除算は加算と減算より強く結合し、どちらも左結合です。
- 比較は**連鎖しません**。`a < b < c` は `(a < b) < c` ではなく構文エラーであり、
  比較は `&&` で組み合わせます。
- ブール演算子の優先順位は固定で、`||` が最も弱くなります。
- 代入のレベルは存在しません。NUDO に可変の束縛があるかどうか自体が未決定だからです。
  図の隙間を埋めるために今このレベルを書くことは、言語機能を発明することになります。
- `ask`、`verify`、`delegate` は演算子ではなく主要式です。これが `verify draft with V`
  を解析可能にしています。`with` は演算子ではなく、`with` で始まる後置形式はないからです。

これを理念ではなく検査可能にしている規則は、**左再帰の禁止**です。再帰下降パーサーは、
自分自身で始まる形式を導出する生成規則を扱えません。この文法の最初の版には四つありました。
それは今やビルドの失敗であり、これから起きる発見ではありません。

フォーマッタは、人間の直感に頼らずに意味を保つだけの構文を出力すべきです。

## 演算子と `if` の基本規則

[NEP-0017](https://github.com/smouj/nudo/blob/main/neps/0017-boolean-comparison-conditionals.md)
は演算子の型と条件式の結果型を定義します。

- `!`、`&&`、`||` は `Bool` を使います。`&&` と `||` は左から右へ評価し、
  短絡します。無効な型のオペランドは演算子位置で `NDO2018` になります。
- 等価比較は `Int`、`Float`、`Bool`、`Text` の同じプリミティブ型で行います。
  順序比較は同じ `Int` または `Float` に限られます。数値変換やユーザー定義の
  オーバーロードはありません。受理済みの `Verified<T>` から `T` へのビューは
  演算子の入力にも適用されます。
- `Float` の比較は IEEE 754 に従います。NaN は自身と等しくなく、順序付けも
  できません。正のゼロと負のゼロは等しい値です。
- `if` の条件は `Bool` です。`else` がある場合、期待型が両方の分岐を検査します。
  期待型がなければ、分岐の型は完全に一致する必要があります。不一致は `else`
  の分岐位置で `NDO2019` になります。
- `else` のない `if` の型は `Unit` であり、`then` 分岐も `Unit` でなければなりません。

実行時には短絡で省略されたオペランドと選択されなかった分岐は評価されません。
静的なエフェクト検査はそのすべてを考慮し、どの入力でも宣言が有効であることを
確認します。

## enum の型付き match

[NEP-0020](https://github.com/smouj/nudo/blob/main/neps/0020-typed-enum-matching.md)
は、ユーザー定義 enum と組み込みの `Result<T, E>` に対する `match` を定義します。
各分岐は宣言済み variant を一つ指定するか `_` を使います。payload はジェネリック
引数を置換した後の宣言型を使い、位置ごとに束縛します。到達可能な wildcard が
残りを受け持たない限り、すべての variant を網羅しなければなりません。不明な名前は
エラーであり、束縛として扱われません。期待結果型がなければ分岐の型は完全一致する
必要があります。期待型があれば、通常の代入規則を各本体に適用します。チェッカーは
パターン、網羅性、分岐のエラーを報告しつつ、各本体の検査も続けます。

```nudo
fn describe(value: Result<Int, Text>) -> Text {
    match value {
        Ok(number) => "success"
        Err(reason) => reason
    }
}
```

パーサーと型チェッカーの適合性ケースでは、ジェネリック payload、`Result`、wildcard、
無効なパターン、エラー回復、分岐型を検証します。チェッカーはまだ `nudo check` に
接続されていません。
