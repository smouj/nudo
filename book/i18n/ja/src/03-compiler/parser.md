# 03.3 — パーサー、無損失構文、AST

> **ステータス:** 実装済み (IMPLEMENTED)  
> **概要:** M2 はトークン列を無損失な構文構造へ変換し、不正な入力から回復し、後続の意味解析段階のために型付き AST を公開しました。

## なぜまず無損失構文なのか

無損失 (lossless) な木はトリビアとソースの全バイトを保持します。この性質は、コメントやレイアウトを黙って破壊することなくコードを変更する必要があるフォーマッタ、エディタツール、自動化エージェントにとって重要です。

パーサーはこれを意図ではなく、検査される性質として保っています。すべてのフィクスチャ、すべての適合性テストケース、すべてのプロパティテストが、木のトークンのテキストを連結するとファイルをバイト単位で再現することを表明します。`nudo check --dump-tree` は木を出力しますが、そのダンプが元のファイルより長いのは、空白とコメントがその中にあるからです。

この正直なコストこそが、木が今の形をしている理由です。`nudo-ast` は木を型付きの値で包みます。名前と本体を持つ `Function`、値を持つ `Binding` などです。そして木がその部分を保持していないときは何も返しません。フォーマッタが書き換えてよいかを判断する場合のように確信を持つ必要がある消費者は、「これは関数だ」と「八番目のトークンまではそう見えていた」を区別できなければなりません。

## エラー回復

有用なパーサーは、最初の欠落トークンで停止しません。回復点には、項目の境界、セミコロン、閉じ区切り文字が含まれ、一つの誤りがファイルの残りをノイズに変えないようにします。

三つの規則がそれを具体的にし、そのそれぞれがテストが見つけた失敗から生まれました。

* **回復は常にトークンを一つ消費するか、停止する。** 回復がループすることはハングであり、ユーザー入力でのハングはバグです。
* **回復はスキップする前に報告する。** 初期の版は配置できなかったものを黙ってスキップし、`nudo check` は理解していなかったファイルに対して `0` で終了していました。これは、呼び出し側がファイルは読まれたと信じるため、ファイルを拒否するよりも悪いことです。
* **一つの位置、一つの診断。** 字句解析器がすでにそのバイトを拒否している場合、パーサーはそのバイトが読めなくした文を報告しません。一文字は一つのメッセージを生み、ファイルを修復するエージェントは一バイトを直します。

パーサーが配置できないトークンは、捨てられるのではなく `Error` ノードに保持されるため、ファイルは依然として再出力できます。誤っている部分も含めて。

## 型付き AST

AST は、下流のパスに生の構文ノードの詳細を知ることを要求せずに、意味的な形 (`Function`、`Call`、`Type`) を与えます。構文から AST への変換はスパンを保持し続け、ノードのスパンは正確にその最初のトークンから始まります。

`nudo-ast` の中で名前を解決したり型を検査したりするものは何もありません。パスは名前のリストであり、参照ではありません。それはマイルストーン M3 であり、パーサーは意図的にそれについて何も知りません。

## 意図的に欠けているもの

* 現時点では何もありません。宣言位置のジェネリックパラメータ (`enum Outcome<T, E>`) と `verify` の名前付きオペランドはどちらも M3.1 以降パースされ、それぞれを固定する適合テストがあります。追加すべき `return` もありません。EBNF は `return` を一度も持ったことがなく、[NEP-0012](https://github.com/smouj/nudo/blob/main/neps/0012-early-exit.md) が、早期脱出は文ではなくブロックの値であると決めました。迷い込んだ `return` は予期しないトークンであり `NDO1001` です。これは `tests/conformance/parser/0017-no-return` によって固定されています。
* 文法のパスは `::` を使い、そのリストはカンマ区切りですが、マニュアルおよび `examples/` のいくつかの例は `web.search` を一行ずつ書いています。パーサーは文法に従います。例はそれらがプレビューであると述べており、この言語がどちらの綴りを持つべきかは NEP であり、パーサーのバグではありません。
